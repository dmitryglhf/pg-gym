Цель — сделать платформу понятной в реальном использовании: **подготовить модель в одном месте, выбрать сценарий работы и наблюдать за результатом без постоянных переходов между разделами**.

Приоритет — UI/UX. Основной сценарий: один GPU. В split-chat один запрос отправляется двум моделям. Консоль остаётся read-only.

**Начать нужно с устранения разрыва между пользовательской задачей и структурой интерфейса.** Сейчас пользователь вынужден знать внутреннее устройство платформы.

| Проблема сейчас                                                  | Что меняем                                                           |
| ---------------------------------------------------------------- | -------------------------------------------------------------------- |
| Ключи и подключения находятся в Settings                         | Переносим подготовку в основной раздел «Модели и серверы»            |
| Inference содержит чат, скачивание и serving                     | Оставляем в Inference разговор и сравнение                           |
| После download/deploy происходит переход на страницу job         | Показываем прогресс в исходном экране, детали открываются по желанию |
| «Скачана», «запущена» и «готова к benchmark» легко перепутать    | Показываем отдельные состояния и доступные возможности               |
| Чат начинается с административной формы создания conversation    | Создаём conversation при первой отправке сообщения                   |
| Недоступная кнопка не всегда объясняет причину                   | Рядом показываем препятствие и действие для его устранения           |
| Console — отдельный раздел                                       | Делаем общую раскрываемую панель активности                          |
| Results смешивает эксперименты, загрузки моделей, серверы и чаты | Организуем историю по понятным категориям                            |

При этом сохраняем существующие полезные решения: preview задачи, advanced-параметры, отдельный учёт execution errors, защиту повторной отправки, поиск в логах и различение heartbeat и реального прогресса.

**1. Перестроить основную навигацию**

Пять основных разделов:

| Раздел               | Основная задача                                                    |
| -------------------- | ------------------------------------------------------------------ |
| **Workspace**        | Понять, что происходит, продолжить работу, посмотреть историю      |
| **Модели и серверы** | Скачать или подключить модель, настроить доступ, запустить serving |
| **Inference**        | Общаться с моделью и сравнивать ответы                             |
| **Benchmarks**       | Проверять модель в выбранном harness                               |
| **Обучение**         | Дообучать модель и оценивать результат                             |

Внизу боковой панели остаются аккаунт, настройки интерфейса и токены доступа к самой платформе.

Provider API keys и HF credentials находятся в «Моделях и серверах». Профили harness открываются из Benchmarks — рядом с местом использования.

Results переносится в историю Workspace, сохраняя прямые ссылки на результаты и сравнение запусков. Console становится общей панелью.

На большом экране — sidebar с понятными текстовыми названиями. При необходимости её можно свернуть до компактного rail.

Выбранная модель, conversation, запуск и фильтры сохраняются в URL. Возврат назад восстанавливает прежний контекст.

**2. Сделать «Модели и серверы» единым центром подготовки**

Основная композиция: список моделей слева, подробности выбранной модели справа. Сверху — «Добавить модель» и краткое состояние ресурсов: например, «GPU свободен» или «GPU занят сервером Qwen».

Карточка модели должна отвечать на четыре вопроса:

* Что это за модель и откуда она появилась?
* Что уже подготовлено?
* Для каких задач она доступна?
* Какое следующее действие?

В карточке показываем название, источник и понятные состояния. Технические ID, revision, файлы и lineage убираем в раскрываемые подробности.

Пример состояний:

| Состояние                         | Основное действие             |
| --------------------------------- | ----------------------------- |
| Модель ещё не скачана             | Скачать                       |
| Модель скачивается                | Посмотреть прогресс           |
| Модель скачана, сервер остановлен | Запустить сервер              |
| Сервер готов                      | Открыть чат                   |
| Запуск заблокирован               | Устранить препятствие         |
| Сервер завершился с ошибкой       | Посмотреть ошибку и повторить |

Рядом — вторичные действия: «Benchmark», «Обучить», «Остановить», «Подробности».

При этом внешний API и локальная модель остаются различимыми. Пользователь не должен ожидать, что внешний endpoint можно дообучить внутри платформы.

Кнопка «Добавить модель» предлагает два пути:

| Источник     | Простая форма                                 | Дополнительные параметры                 |
| ------------ | --------------------------------------------- | ---------------------------------------- |
| Hugging Face | Repository и токен при необходимости          | Revision, имя, существующая переменная   |
| Внешний API  | URL, model identifier, ключ при необходимости | Context/output limits, tool calling, имя |

**Ключ добавляется прямо в этой форме.** Можно выбрать существующую переменную или создать новую во вложенной панели. После сохранения пользователь возвращается к незавершённой настройке модели.

Полный `.env`-редактор сохраняем как расширенный инструмент этого раздела. Для обычного подключения он не нужен.

Во время скачивания пользователь остаётся на карточке модели. После завершения сразу видит две возможные ветки: «Запустить сервер» и «Обучить».

**3. Упростить настройку serving**

В простом режиме нужны:

* Выбранная модель.
* Назначение: «Чат» или «Чат и harness».
* Краткая информация о готовности ресурса.
* Кнопка «Запустить сервер».

Context window, GPU memory fraction и tool parser находятся в дополнительных параметрах.

Для известных сочетаний модели и runtime можно предложить проверенные пресеты. Для неизвестного сочетания нельзя автоматически выбирать parser только ради сокращения формы.

Состояния сервера должны быть понятными:

| Состояние    | Что видит пользователь                                        |
| ------------ | ------------------------------------------------------------- |
| Ожидание     | Причина ожидания и доступное действие                         |
| Подготовка   | Подготавливаются файлы и окружение                            |
| Загрузка     | Модель загружается                                            |
| Готов        | Можно открыть чат или benchmark                               |
| Потеря связи | Последнее известное состояние и время обновления              |
| Ошибка       | Краткое объяснение и переход к журналу                        |
| Остановка    | Запрошена остановка, освобождение ресурса ещё не подтверждено |

Работающий сервер отображается как **«Готов»**, без вечного индикатора незавершённой операции.

Если точная причина очереди неизвестна, интерфейс сообщает это прямо. Процент готовности и ETA показываем только при наличии соответствующих данных.

**4. Переделать Inference вокруг разговора**

Основной сценарий: **выбрать модель → написать сообщение**.

Композиция экрана:

| Зона                          | Содержимое                                          |
| ----------------------------- | --------------------------------------------------- |
| Верхняя панель                | Модель, статус, «Сравнить», «Развернуть», настройки |
| Основная область              | Сообщения                                           |
| Нижняя панель                 | Закреплённое поле ввода и отправка                  |
| Сворачиваемая боковая область | История разговоров                                  |

Conversation создаётся при первой отправке. Название назначается автоматически. Отдельная форма «создать разговор» исчезает.

На пустом экране достаточно короткой подсказки и нескольких примеров, связанных с платформой: объяснить SQL, разобрать ошибку, проверить diff.

Параметры генерации открываются по кнопке настроек. Они не занимают основной экран.

Если доступных моделей нет, показываем действие «Подключить или запустить модель». Оно ведёт в подготовку с последующим возвратом в чат и сохранением черновика.

В picker можно показывать недоступные модели, но обязательно с причиной: «Сервер остановлен», «Ещё скачивается», «Нет связи».

**5. Сделать полноценный split-chat**

Кнопка «Сравнить» добавляет модель B.

Сразу появляются две устойчивые колонки. Общий пользовательский запрос отображается один раз; у каждой модели собственный ответ и собственный статус.

Основные правила:

* Один composer отправляет одинаковый запрос обеим моделям.
* Параметры сравнения доступны через общие настройки.
* Колонки не появляются и не перестраиваются во время генерации.
* Ошибка или ожидание одной модели обозначаются в её колонке.
* Копирование ответа доступно отдельно для каждой модели.
* История пользовательских запросов общая, история ответов у каждой модели своя.

Текущий backend генерирует ответы последовательно. Поэтому у B должно отображаться «Начнёт после модели A», пока её генерация не началась.

«Развернуть» переводит сравнение в режим фокуса: скрываются основная навигация, история и консоль. Две колонки занимают доступную ширину окна, composer остаётся внизу.

При выходе через кнопку или Escape сохраняются модели, сообщения, черновик и положение интерфейса.

На узком экране используем переключение A/B вместо двух слишком узких колонок.

С учётом одного GPU первоначально поддерживаем сравнение локальной модели с внешним endpoint либо двух внешних endpoint. Автоматическое переключение двух локальных моделей на одном GPU — отдельный будущий сценарий.

**6. Упростить Benchmarks**

Порядок формы должен соответствовать решениям пользователя:

1. **Модель** — автоматически выбрана при переходе из её карточки.
2. **Что проверяем** — suite, затем одна задача или набор/split.
3. **Harness** — Markov или OpenCode.
4. **Проверка перед запуском** — объём работы, готовность, основная кнопка.

Preview задачи сохраняем во вспомогательной панели.

Название запуска, timeout, maximum turns и harness profiles находятся в дополнительных параметрах.

Недоступность запуска объясняем возле кнопки:

| Препятствие                      | Действие                          |
| -------------------------------- | --------------------------------- |
| Нет модели                       | Подключить или запустить          |
| Модель настроена только для чата | Настроить использование в harness |
| Нет подходящего worker           | Посмотреть состояние ресурсов     |
| Модель недоступна                | Проверить подключение             |

После отправки остаёмся в контексте benchmark: показываем статус и открываем общую панель активности. Полная страница запуска остаётся доступна отдельно.

**7. Сделать «Обучение» самостоятельным понятным сценарием**

В навигации используем название «Обучение». GRPO остаётся названием метода внутри экрана.

Простая форма:

* Базовая модель.
* Suite и split.
* Объём обучения или проверенный профиль.
* Готовность ресурса.
* Запуск.

Learning rate, group size, LoRA и остальные параметры сохраняются в advanced. Пресет «рекомендуемый» появляется только после проверки соответствующей конфигурации.

Оценка модели — второй режим этого раздела. Явно различаем direct-patch evaluation и benchmark в harness: они измеряют разные сценарии.

Serving перед обучением не требуется.

Если единственный GPU занят сервером, показываем это до отправки задачи: «GPU занят сервером Qwen». Рядом — «Остановить сервер», с объяснением последствий для использующих его чатов и benchmark.

После подтверждённого освобождения ресурса можно запустить обучение, сохранив заполненную форму. В первой версии это две понятные операции.

После обучения показываем следующие действия: «Оценить», «Подготовить к чату», «Benchmark». Если требуется подготовить адаптер к serving, сохраняем исходную цель перехода.

**8. Перестроить Workspace и общую консоль**

Workspace отвечает на вопросы: что сейчас происходит, что мешает работе и что можно сделать следующим.

Для нового пользователя показываем выбор намерения: подключить модель, скачать модель, запустить доступный benchmark. Вместо обязательной цепочки настройки учитываем уже готовые ресурсы.

Для настроенного workspace основной порядок такой:

1. Активные операции и препятствия.
2. Следующее доступное действие.
3. Недавние эксперименты.
4. История запусков.
5. Ресурсы и подробная диагностика.

Историю разделяем на категории «Эксперименты», «Модели и серверы», «Чаты». Колонки соответствуют категории: серверу не нужна колонка Reward.

Консоль становится общей раскрываемой панелью, доступной из любого раздела. В Workspace её можно развернуть полностью.

Сохраняем:

* Выбор job.
* Поиск и фильтр событий.
* Автопрокрутку.
* Экспорт текущего вида.
* Состояние подключения и давность обновления.
* Read-only режим.

При переходе между разделами выбранная job сохраняется. «Открыть логи» привязывает панель к соответствующему запуску.

При ручной прокрутке вверх автопрокрутка приостанавливается. Новые записи обозначаются кнопкой перехода вниз.

В split-chat консоль по умолчанию свёрнута.

**9. Применить визуальное направление Cohere и принципы Material**

Из присланного Cohere берём спокойную светлую поверхность, компактную навигацию, минимальную панель инструментов, центральную область разговора и закреплённый composer.

Для подготовки моделей и истории сохраняем достаточную плотность информации. Большие пустые пространства чатового welcome screen здесь не помогают.

Для моделей подходит компоновка «список — детали», для benchmark с preview — основная и вспомогательная панели. Эти подходы соответствуют [Material canonical layouts](https://m3.material.io/foundations/layout/canonical-examples/overview).

Общие правила:

* Одно заметное основное действие для текущей задачи.
* Связанные поля находятся рядом.
* Редкие параметры раскрываются по необходимости.
* Состояния обозначаются текстом и иконкой, цвет дополняет их.
* Ошибка появляется рядом с местом исправления.
* Длительная операция имеет устойчивое представление на экране.
* Заблокированная операция показывает причину и следующее действие.
* Клавиатурная навигация, видимый фокус и возврат фокуса после закрытия панели входят в проектирование.
* Переходы и раскрытия учитывают reduced motion.

Шрифты, скругления и тени полируем после согласования маршрутов.

Критика:

**Главный недостаток плана — хорошо описаны экраны и запуск действий, но недостаточно описано продолжение работы после этих действий.** Ниже — конкретные пробелы, которые стоит закрыть до макетов.

1. **Не определено, что именно представляет карточка модели.**

   Мы объединили модель, артефакт, сервер и подключение в один раздел, но оставили неясной их связь внутри интерфейса. У базовой модели появляются обученные варианты, а сервер можно остановить и запустить заново. Поэтому надпись «Готова» и кнопка «Benchmark» без выбранного варианта и сервера неоднозначны.

   **Поправка:** карточка должна явно показывать выбранный вариант модели и связанный с ним сервер. Действия относятся к этому выбору. Внешнее подключение отображается как отдельный тип источника, без действий скачивания и обучения.

2. **Основное действие зависит только от состояния, хотя должно учитывать цель пользователя.**

   В плане у готового сервера основная кнопка — «Открыть чат». Но если пользователь пришёл подготовить модель из Benchmark, после подготовки ему нужен возврат к заполненному benchmark. Сейчас в плане это правило описано только для некоторых переходов.

   **Поправка:** зафиксировать сквозной сценарий: «начал benchmark → подготовил недостающую модель → вернулся в тот же benchmark с сохранёнными параметрами». Аналогично для обучения и чата. Завершение подготовки возвращает к исходной задаче.

3. **Сценарий одного GPU заканчивается на запуске обучения. Обратный путь отсутствует.**

   Мы предложили остановить serving, обучить модель и затем снова использовать её. Но не определили, что произойдёт с прежними чатами и выбранными подключениями.

   Это уже конкретный разрыв: текущий backend создаёт для нового deployment новое подключение, а существующий conversation сохраняет прежнее. Повторный запуск сервера сам по себе не восстанавливает старый чат.

   **Поправка:** спроектировать весь цикл: работающий сервер → остановка → обучение → выбор исходной или обученной модели → запуск → продолжение использования. Для старого чата явно определить доступное действие. Нельзя обещать «Продолжить», если фактически создаётся пустой разговор.

4. **У split-chat описана раскладка, но не определено поведение незавершённого сообщения.**

   Что означает «Стоп»: остановить весь запрос или одну модель? Что делать, если A ответила, а B завершилась с ошибкой? Какой ответ попадёт в контекст следующего сообщения?

   Последний вопрос особенно важен: сейчас неуспешный ход целиком исключается из истории для следующих запросов, даже если частичный результат содержит законченный ответ A. На экране ответ виден, но модель в дальнейшем его не учитывает.

   **Поправка:** определить единицу взаимодействия — общий ход с двумя отдельными результатами. Зафиксировать остановку, повтор, сохранение успешного ответа и продолжение истории. Желаемое поведение — ошибка B не обесценивает законченный ответ A; необходимое изменение контракта отметить отдельно.

5. **Не спроектирован главный экран после завершения эксперимента.**

   В плане подробно описано, как запустить benchmark и обучение. Дальше стоят ссылки «Результаты», «Оценить», «Benchmark», но отсутствует ответ на основной платформенный вопрос: **что получилось и стало ли лучше?**

   **Поправка:** добавить сценарий разбора результата:

   * Краткий итог и полнота выполнения.
   * Решённые задачи отдельно от ошибок исполнения.
   * Переход к конкретной неудачной задаче.
   * Сравнение с выбранным исходным запуском при совместимых условиях.
   * Повтор с изменением параметров без заполнения формы заново.

   Для обучения также нужна очевидная связь «базовая модель → полученный вариант → его оценка». Это часть основного рабочего цикла.

6. **Перенос Results в Workspace пока описан слишком расплывчато.**

   Workspace уже содержит onboarding, активные операции, следующие действия, ресурсы, историю и консоль. При этом регулярный доступ к результатам мы убрали из основной навигации, не определив равноценный вход.

   **Поправка:** внутри Workspace сразу закрепить два постоянных представления: **«Обзор» и «Запуски»**. У запусков — собственный адрес, сохранённые фильтры и прямой вход в результат. История не должна быть секцией, которую каждый раз приходится искать ниже dashboard.

7. **У общей консоли противоречивые правила переключения.**

   Мы одновременно обещаем сохранять выбранную job при навигации и автоматически открывать активность нового запуска. Не определено, что происходит, когда пользователь читает старые логи и запускает новую задачу.

   **Поправка:** консоль меняет выбранный запуск только по явному действию пользователя. Новый запуск получает компактное подтверждение с кнопкой «Открыть логи». Различаем два действия: свернуть панель и прекратить следовать за её выводом. Они не должны менять выбранную job.

8. **Не определено, когда «Запустить» действительно запускает, а когда ставит в очередь.**

   В плане есть проверки готовности и объяснения занятости, но нет окончательного правила для основной кнопки. Это оставляет исходную проблему: пользователь нажимает действие с одним обещанием и получает другое.

   **Поправка:** различать три ситуации:

   | Ситуация                     | Поведение                                                             |
   | ---------------------------- | --------------------------------------------------------------------- |
   | Всё необходимое доступно     | «Запустить»                                                           |
   | Ресурс временно занят        | Явное «Поставить в очередь», если пользователь выбирает ожидание      |
   | Запуск требует вмешательства | Действие устранения причины: настроить, подключить, остановить сервер |

   Для постоянно работающего serving нужно прямо объяснить: очередь не освободится сама, пока сервер не остановлен.

Я бы **до отрисовки экранов дополнил план тремя сквозными сценариями**: возврат из подготовки в исходную задачу; полный цикл работы на одном GPU; разбор и повтор эксперимента после результата. Затем отдельно зафиксировал поведение одного хода split-chat. Эти решения сейчас определяют, получится ли связный рабочий интерфейс.
