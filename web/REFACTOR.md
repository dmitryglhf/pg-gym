# Рефакторинг web/: UI/UX платформы

Дата: 16 сентября 2026 года. Итоговый накопительный срез 06.

Архив содержит полную директорию `web/`. Замените ей текущую директорию frontend.
Бэкенд и его API этим архивом не изменяются. Существующие команды Deno сохранены.

## Что изменилось

- Основная навигация: Workspace, Models & servers, Inference, Benchmarks, Training.
  Компактная плавающая панель оформлена как в исходном интерфейсе: без логотипа и сворачивания, с одной кнопкой Workspace. На узком экране она расположена снизу.
- Workspace: выбор цели, подготовка под конкретную задачу, ресурсы, активные операции,
  Runs & results. История разделяет эксперименты, модели/серверы и чаты; фильтры доступны по URL.
- Models & servers: единый список локальных моделей, адаптеров и внешних endpoint;
  Hugging Face import, ключи и переменные внутри подготовки, serving, состояние сервера,
  остановка, проверка и переход к использованию. «Files ready» отделено от готовности сервера.
- Inference: создание диалога первой отправкой, общий prompt двум моделям, устойчивые
  колонки A/B, мобильное переключение A/B, история, fullscreen, копирование и JSON export.
  После остановки managed-сервера старое подключение не считается готовым.
- Benchmarks: модель → задача/набор → harness; preview сохранён. Профили находятся здесь,
  выбранный профиль явно показывает применяемые лимиты. Повтор с изменениями переносит
  исходный набор задач, а не автоматически заменяет его целой suite.
- Training: использует скачанные веса без обязательного serving. При известном занятом
  GPU можно подтвердить остановку сервера или явно выбрать очередь. Learning rate,
  group size, LoRA и generation-параметры находятся в advanced.
- Отправка операций сохраняет исходный экран и показывает карточку результата.
  Общая read-only activity-панель сохраняет выбранную job, имеет поиск и фильтры,
  экспорт, ручную паузу follow, сворачивание и расширение. Submit не переключает её job.
- Черновики benchmark, training и chat сохраняются в sessionStorage при каждом изменении.
  Секреты туда не записываются. Выход и смена аккаунта очищают данные предыдущего пользователя.
- Старые URL для подготовки в Inference/Settings и отдельной Console перенаправляются
  в новые разделы. Ссылки на jobs, conversations и результаты сохраняются.

## Организация кода

- `islands/Platform.tsx` — сборка экрана и независимая загрузка нужных ресурсов.
- `components/models/` — добавление модели, карточка артефакта, карточка подключения.
- `components/inference/ChatTurn.tsx` — поток ответов и стабильное отображение A/B.
- `components/ResultsPanel.tsx`, `ProfilesPanel.tsx` — история и контекстные профили.
- `components/OperationCard.tsx`, `CredentialPicker.tsx` — общие взаимодействия.
- `islands/ActivityDock.tsx` — общая панель событий.
- `lib/query.ts` — обновление данных, ошибки, сохранение последнего полученного состояния,
  обход страниц deployment history.
- `lib/readiness.ts` — готовность подключений и известная занятость GPU.
- `lib/workspace.ts` — черновики, сохранение контекста и переходы между задачами.
- `assets/workspace.css` — общая оболочка и новые экраны поверх существующих примитивов.

## Границы текущего API

1. A/B выполняется последовательно: сначала A, затем B. Если весь turn завершился ошибкой,
   backend исключает его из последующей истории, включая сохранённый частичный ответ A.
   Интерфейс объясняет это; отдельного retry стороны B нет.
2. Один worker не обслуживает два local deployment одновременно. Для сравнения на одном
   GPU используйте локальный сервер и внешний endpoint либо два внешних endpoint.
3. Перезапуск deployment создаёт новое подключение. Старые conversation неизменяемы;
   продолжение с новым подключением создаёт новый чат, история прежнего остаётся доступна.
4. Connection Check подтверждает наличие модели в `/models`; это не тест tool calling.
5. API не даёт полной причины каждой очереди и ресурсов других владельцев. UI показывает
   подтверждённые возможности worker и известные блокировки. Recent jobs ограничены 200,
   deployment history обходится полностью; история запусков расширяется кнопкой загрузки.
   Причина исходного зависания serving не исправлялась на стороне scheduler этим frontend.
6. Создание conversation не имеет серверной дедупликации. После неоднозначной ошибки
   интерфейс предлагает проверить History; уже полученный ID сохраняется до отправки turn.
   Идемпотентные submit-запросы повторно используют прежний ключ при потере подтверждения.
7. При Edit & run again задачи разрешаются заново на сервере. Скопированные лимиты сохраняются;
   temperature/context strategy старого harness-профиля требуют выбора соответствующего профиля.
   Для точной серверной копии есть Queue saved configuration на экране запуска.
8. Черновики предназначены для текущей вкладки/сессии браузера, не для синхронизации устройств.
   История conversation ограничена последними 200 записями существующим API.

## Проверка

Локально выполнены:

- форматирование Deno и lint;
- отдельная строгая TypeScript-проверка components, islands и lib;
- 7 изолированных тестов: существующие activity/environment и новые случаи readiness.

Полная Fresh typecheck остановилась на загрузке JSR `@fresh/core` в данном окружении.
Framework build, браузерная интеграция, реальные GPU/vLLM, скачивание, benchmark и обучение
здесь не подтверждены. Их функциональную проверку выполняет владелец платформы.

Ключевые маршруты для проверки: HF → download → serving → chat; внешний endpoint →
benchmark; занятый serving GPU → подтверждённая остановка → training → adapter → evaluation.
Также: возврат из подготовки к черновику, A/B failure, смена endpoint после restart,
сохранение выбранной job в console и работа Back/refresh.
